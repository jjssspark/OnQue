# AI 호출 예산 설계 — 하루 20건으로 살아남기

작성일 2026-08-17

## 목표

Gemini 무료 티어의 하루 20건 한도를 스윕·요약·비서·채팅이 나눠 쓰는 구조를 세운다.

두 가지를 동시에 한다. **파이를 나누는 것**(예산 장부와 배분 규칙)과 **파이를 키우는
것**(중복 호출 제거). 나누기만으로는 부족하다 — 지금 채팅 메시지 하나가 2건을 쓰고
있어, 사용자 몫 12건이 메시지 6개밖에 안 된다.

한도를 늘리는 작업이 아니다. 유료 전환은 하지 않기로 정했다. 주어진 20건 안에서
**사용자가 시킨 일이 실패하지 않게** 만드는 작업이다.

## 배경 — 코드에서 확인한 사실

확인한 것만 적는다. 추측은 포함하지 않는다.

### 소비자별 실제 호출 수 (사용자 행동 1회당)

| `/문서` | **2건** | `main.py:1009,1021` | 없음 |
| `/요약` | 1건 | `main.py:1004` | 없음 |

| `/질문` | 1건 | `main.py:1052` | 없음 |
| 비서 질문 | 1건 | `routers/assistant.py:53` | 없음 |

| 스윕 | 방당 1건 | `commitment_service.py:302` | 하루 8건 |

**하루 20건은 채팅 메시지 10개다.** 스윕이 8건을 선점하면 사용자에게 남는 12건은
메시지 6개 또는 `/문서` 6번이다.

### 확인된 낭비

`_SUMMARY_SCHEMA`는 `category`를 필수 필드로 갖는다(`gemini_service.py:235,240`).
`/문서`가 쓰는 `draft_document_from_conversation`도 이 스키마로 응답을 받는다(`:644`).

그런데 `main.py:1021`은 그 값을 버리고 `classify_document_category`를 **무조건 다시
부른다.** 업로드 경로(`main.py:218`)는 이미 폴백으로만 부르도록 고쳐져 있다.

**같은 수정이 두 경로 중 한 곳에만 적용된 상태다.** TS-035(`korean_date_context()`를
호출부 여섯 곳 중 둘에 빠뜨림)와 같은 모양의 누락이다.

### 이미 존재하는 병합 전례

`answer_assistant`(`gemini_service.py:755`)는 한 번의 호출로 답변과 액션 제안을 함께
받는다(`_ASSISTANT_RESPONSE_SCHEMA`에 `reply` + `actions`). 채팅방 경로만 같은 일을
두 번 나눠 부르고 있다.

### 현재 가드의 한계

`SweepBudget`(`models.py:293`)은 스윕이 쓴 수만 센다. 요약·비서·채팅은 장부에 잡히지
않아, 소진되면 사용자는 429를 받는다. `routers/assistant.py:57`이 429로 내리고 있으나
다른 경로는 안내가 "잠시 후 다시"다 — **하루 한도는 잠시 후에 안 풀린다.**

## 설계

### 1. 배분 정책 — 예비선 방식

장부 하나에 총 사용량만 기록하고, 소비자별 상한을 다르게 둔다.

```
잔량 20 ────────────────────────────── 0
        │   스윕이 도는 구간   │   예비선=12   │
사용자  │●●●●●●●● 쓸 수 있음 ●●●●●●●●●●●●●●●│
스윕    │●●●●●●●●│      멈춤              │
```

```
user  : calls < DAILY_TOTAL            (20)
sweep : calls < DAILY_TOTAL - RESERVE  (8)
```

고정 분할(장부 2개)을 택하지 않은 이유: 스윕이 3건만 쓴 날에도 사용자가 12에서
막힌다. 예비선 방식은 남은 것을 사용자가 전부 쓸 수 있다.

양쪽 최소 보장(예약 + 공유 구간)을 택하지 않은 이유: 상태가 셋이라 경계값 조합이
6지점으로 늘고, 사용자가 잔량을 예측하기 어렵다.

**원칙은 기존 코드에 이미 적혀 있다** — *"시킨 일이 안 시킨 일 때문에 실패하는 것이
한도 자체보다 나쁘다"*(`commitment_service.py:196`). 예비선은 이 문장을 규칙으로
옮긴 것이다.

### 2. 모듈 — `call_budget.py`

공개 함수 셋.

```
claim(db, consumer) -> bool     # 1건 선점. consumer는 "user" | "sweep"
remaining(db) -> int            # 잔량. 화면·사전 차단용
user_claimer() -> Callable[[], bool]
        # gemini_service에 넘길 호출 가능 객체. 부르면 별도 세션을 열어
        # "user" 몫 1건을 선점하고 닫는다. 라우터가 세션을 넘기지 않아도
        # 되게 하려는 것 — 게이트웨이는 DB를 모른 채 이것만 부른다.
```

설정값. 모두 환경변수로 덮어쓸 수 있다.

```
DAILY_TOTAL = 20
RESERVE     = 12
RESET_AT    = 리셋 시각 (아래 미해결 항목 참조)
```

선점 방식은 기존 `_claim_sweep_call`(`commitment_service.py:209`)을 그대로 가져온다.
조건부 UPDATE의 rowcount로 판정하고, 오늘 행이 없으면 SAVEPOINT 안에서 삽입을
시도하며, 경합에 지면 UPDATE로 재시도한다. 이미 동시성 함정을 다 밟아본 코드라 새로
쓸 이유가 없다. 상한만 소비자별로 달라진다.

**테이블은 `sweep_budget` → `call_budget`으로 개명한다.** 의미가 "스윕이 쓴 수"에서
"전체 소비"로 바뀌는데 이름을 두면 거짓말이 된다. `scripts/migrate_add_sweep_stats.py`
전례를 따라 이관 스크립트를 둔다.

### 3. 게이트웨이 — 빠뜨릴 수 없게 만드는 법

`gemini_service`의 9개 `generate_content` 호출을 단일 래퍼로 통과시킨다. 차감과 거부가
한 곳에서 일어난다.

`gemini_service`는 DB를 모르는 계층이므로 세션을 넘기지 않는다. 대신 각 공개 함수가
**`claim: Callable[[], bool]`을 필수 인자로 받는다.**

```
라우터 (쓰기 트랜잭션 진행 중)
  └ gemini_service.chat_reply_with_actions(claim=call_budget.user_claimer(), …)
        └ 래퍼: claim()  ──▶ 별도 세션 → 조건부 UPDATE → 커밋 → 닫기
                 │
                 ├ False ─▶ QuotaExceeded
                 └ True  ─▶ generate_content
```

**필수 인자인 것이 이 설계의 핵심이다.** TS-035는 선택적 컨텍스트를 빠뜨려도 조용히
잘 돌아간 것이 문제였다 — 테스트 265개가 전부 초록인데 마감일이 799일 어긋나 있었다.
필수 인자는 빠뜨리면 `TypeError`로 즉시 터지므로, 새 호출 경로가 생겨도 예산을 우회할
수 없다.

전역 등록(`set_budget_manager`) 방식은 호출부 변경이 0인 대신 전역 상태가 생기고
테스트 격리가 깨져서 택하지 않았다.

### 4. 차감 트랜잭션 — 별도 세션에서 즉시 커밋

장부 차감은 요청 트랜잭션과 **분리된 세션**에서 하고 곧바로 커밋한다.

이유는 기존 코드가 이미 적어둔 것과 같다(`commitment_service.py:220`) — 실제 Gemini
한도는 롤백되지 않는다. 바깥 트랜잭션이 실패해 되돌아가면 장부만 복구되고 한도는 깎인
채 남는다. 그 경로가 실패를 반복하면 남은 예산을 전부 태우면서 장부는 여유가 있다고
말한다.

기존 `_claim_sweep_call`은 약속 목록 **조회**(읽기 전용) 중에 불려서 같은 세션이어도
무해했다. 채팅 메시지 POST는 쓰기 트랜잭션 한가운데라, 같은 세션에서 커밋하면 아직
완성되지 않은 상태까지 함께 커밋된다.

DB는 Postgres(Neon, `db.py:18`)라 별도 커넥션 동시 쓰기에 락 문제가 없다.

**선차감을 유지한다.** 호출이 실패해도 되돌리지 않는다 — 요청이 나갔으면 한도는 이미
깎였고, 되돌리면 실패 재시도가 한도를 태운다.

### 5. 소비 절감

**(a) `/문서` 2건 → 1건.** `main.py:1021`을 `main.py:218`과 같은 폴백 형태로 바꾼다.
이미 받아온 `structured["category"]`를 쓰고, 없을 때만 `classify_document_category`를
부른다. 새 코드가 아니라 이미 있는 패턴을 빠진 곳에 적용하는 것이다.

**(b) 일반 메시지 2건 → 1건.** `extract_chat_actions` + `generate_bot_reply`를
`chat_reply_with_actions` 하나로 합친다. 스키마는 `_EXTRACTION_SCHEMA`에 `reply: STRING`을
더한 형태이며, `_ASSISTANT_RESPONSE_SCHEMA`와 같은 구조다.

`/할일`은 `extract_chat_actions`를 답변 없이 재사용하므로 그대로 둔다.

**효과**: 사용자 몫 12건이 메시지 6개 → **12개**, `/문서` 6번 → **12번**.

**(b)가 감수하는 대가 둘.**

첫째, 프롬프트가 겸업한다. 지금은 추출 지시(*"잡담은 무시. 날짜는 절대 날짜로."*)와
페르소나 지시(*"꼼꼼한 PM 비서. 2~4문장 친근하게."*)가 분리돼 각자 한 가지만 시킨다.
합치면 하나가 둘을 다 담는다. 품질이 떨어질지는 해보기 전엔 모른다. 근거는
`answer_assistant`가 이미 같은 겸업으로 돌고 있다는 전례뿐이므로, **구현 중 같은 입력에
대한 병합 전후 출력을 직접 비교해 확인한다.**

둘째, 실패 격리가 사라진다. 지금은 추출이 실패해도(`gemini_service.py:592`가 빈 결과를
돌려주고 넘어감) 답변은 정상적으로 나간다. 합치면 한 번의 실패가 둘 다 잃는다. 반대급부로
실패 시 호출이 1건만 소모된다.

### 6. 응답 형식

`meta.sweep`에 있던 예산 필드를 밖으로 꺼낸다. 이제 스윕 소속이 아니다.

```jsonc
"meta": {
  "sweep":     { "last_at": "2026-08-17T11:48:00Z", "scanned": 34, "found": 2 },
  "ai_budget": { "used": 7, "total": 20, "resets_at": "2026-08-18T00:00:00Z" }
}
```

(위 값은 형식을 보이기 위한 예시다. 시각은 ISO 8601 UTC 문자열이다.)

프론트는 `SweepMeta`에서 예산 두 필드를 빼고 `AiBudget` 타입을 새로 둔다.
`buildSweepStatus`의 `exhausted` 판정도 그쪽으로 옮긴다.

**소진 시 응답**: HTTP 429 + `error.code = "AI_DAILY_BUDGET_EXHAUSTED"`. 스윕·요약·
비서·채팅 전 경로를 이 코드로 통일한다.

### 7. 화면

잔량은 이미 있는 통로로 흐른다 — `WorkspaceContext`가 `/api/v1/commitments`를 30초마다
조회하고 있어, 프론트 어디서든 최신 잔량을 안다.

**사전 차단 세 곳**: 채팅 입력창(AI가 방에 있을 때), 비서 입력창, 업로드 버튼. 잔량 0이면
입력을 막고 그 자리에 사유를 쓴다.

> 오늘 AI 한도를 다 썼습니다. 내일 오전 9시에 초기화됩니다.

(문구의 시각은 `RESET_AT` 실측값으로 채운다. 아래 미해결 항목 참조.)

대시보드의 "오늘 3/8"은 "오늘 7/20"이 된다.

잔량이 적을 때 미리 경고하는 것은 넣지 않는다. 상태가 하나 더 늘고, 0이 아닌 이상 쓸 수
있다는 편이 단순하다.

화면 차단은 헛수고를 없애는 것이지 보안이 아니다. **서버는 여전히 막는다.**

## 테스트

핵심은 게이트웨이가 실제로 강제되는지를 **자동으로** 확인하는 것이다.

`gemini_service`의 공개 함수를 `inspect.signature`로 순회해 전부 `claim`을 필수 인자로
받는지 검사한다. 누가 나중에 새 Gemini 호출 함수를 추가하면서 예산을 빠뜨려도 테스트가
잡는다. TS-035가 "테스트 265개 전부 초록인데 여섯 곳 중 둘이 빠져 있던" 사건이었으므로,
그 실패를 자동화로 막는 것이 이 설계의 값어치다.

| 대상 | 확인할 것 |
|---|---|
| `call_budget` | 예비선 규칙 — `sweep`은 잔량 12(누적 8건)에서 멈추고 `user`는 0까지 간다 |
| | 동시 선점에서 총량 초과 없음 |
| | 하루 경계에서 장부가 새로 시작됨 |
| | `DAILY_TOTAL=0` 설정에서 아무도 못 쓴다 |
| | 차감이 바깥 트랜잭션 롤백에 영향받지 않음 |
| 게이트웨이 | 공개 함수 전부가 `claim`을 필수 인자로 받음 (시그니처 순회) |
| | `claim`이 False면 `QuotaExceeded`, `generate_content`는 안 불림 |
| 병합 함수 | 답변과 액션을 한 응답에서 받음 |
| | 실패 시 동작 (답변·액션 모두 없음) |
| `/문서` | `structured`에 category가 있으면 `classify_document_category`를 안 부름 |
| 라우터 | 소진 시 429 + `AI_DAILY_BUDGET_EXHAUSTED` — 스윕·요약·비서·채팅 전 경로 |
| 프론트 | 잔량 0에서 세 입력구가 비활성 + 리셋 문구 노출 |
| | `AiBudget` 타입 분리 후 `buildSweepStatus` 회귀 |
| 회귀 | 기존 백엔드 280건 / 프론트 25건 |

## 미해결로 남기는 것

**리셋 시각을 검증하지 않았다.** 현재 코드는 UTC 자정 기준으로 하루를 센다
(`commitment_service.py:204`). Gemini 무료 티어의 실제 리셋 시각이 UTC 자정인지는 확인한
적이 없다. 어긋나면 화면의 리셋 안내가 틀린 시각을 말하게 된다.

설계에서는 `RESET_AT`을 설정값으로 빼두고, **구현 중 실측해 채운다.** 실측 전까지는
UTC 자정을 기본값으로 둔다.

**병합(5-b)의 품질 영향은 구현 전에 알 수 없다.** 같은 입력에 대한 병합 전후 출력을
직접 비교해 확인하고, 눈에 띄게 나빠지면 되돌린다. 되돌리는 비용은 낮다 — 두 함수를
지우지 않고 남겨두면 호출부 한 줄로 복귀한다.

**소비자별 사용 내역은 남기지 않는다.** 장부는 총량 하나만 센다. 누가 얼마나 썼는지는
구조화 로그(`event`, `consumer`)로 남기고, 집계가 필요해지면 그때 뽑는다. 화면에는 총량만
필요하다.
