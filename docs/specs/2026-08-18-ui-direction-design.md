# UI 방향 재설정 설계 — 템플릿을 벗고 처리 도구로

작성일 2026-08-18

## 목표

화면이 "AI가 대충 만든 템플릿" 같다는 문제를 푼다. 색 몇 개를 바꾸는 일이 아니라
기조와 구성을 다시 잡는 일이다.

두 가지를 한다. 색과 글꼴을 푸른 기조로 다시 정하는 것, 그리고 대시보드 구성을
모니터링 형태에서 처리 형태로 바꾸는 것.

기능을 추가하거나 빼는 작업이 아니다. 지금 있는 데이터와 API는 그대로 두고
보여주는 방식만 바꾼다.

## 배경 — 코드에서 확인한 사실

확인한 것만 적는다.

### 지금 토큰

`app/globals.css`에 정의되어 있다.

| 토큰 | 값 | 성격 |
|---|---|---|
| `--background` | `#07080E` | 거의 검정 |
| `--surface` | `#12151F` | 카드 |
| `--brand` | `#7C8CFF` | 보라빛 인디고 |
| 글꼴 | Geist Sans / Geist Mono | |

이 세 가지는 Next.js 스타터를 깔면 딸려오는 기본값이다. 어떤 서비스에 붙여도 같은
인상이 나는 게 템플릿처럼 보이는 직접적인 원인이다.

### 토큰 밖 하드코딩 색

`app/`과 `components/`의 tsx에서 세었다. 총 111곳.

| 클래스 | 횟수 | 라이트 전환 시 |

| `bg-white` | 22 | 배경과 구분 안 됨 |

| `text-red-300` | 9 | 흰 바탕에서 너무 옅음 |
| `text-red-400` | 6 | 같음 |
| `text-emerald-300` | 6 | 같음 |
| `bg-emerald-500` | 6 | |

토큰만 바꾸면 이 111곳이 그대로 남아 화면이 깨진다. 색 전환이 이 작업의 실제 분량이다.

### 개편 상태

12개 화면 중 3개만 2026-08-11 개편을 거쳤다. `globals.css` 주석이 그 사실을 적고 있다.

> 개편하지 않은 9개 화면이 border-border에 의존한다. 지우면 그 화면들이 한 덩어리로
> 뭉개지므로, 값만 약화시켜 새 밝기 대비로 넘어가게 한다.

즉 화면 사이 불일치는 이미 있고, 그 개편의 규칙이 옳았는지는 검증된 적이 없다.

### 구성 문제

지표 카드 네 개를 위에 깔고 목록을 아래 붙인 형태다. 이건 Datadog이나 Grafana 같은
모니터링 도구에서 온 구성이고, 숫자를 지켜보는 화면에서는 맞다.

OnQue는 지켜보는 도구가 아니라 처리하는 도구다. Linear는 지표 카드가 아예 없고 숫자를
필터 버튼 안에 넣는다. Things는 할 일과 일정을 오늘 한 뷰에 섞는다. Superhuman은
목록과 상세를 나란히 놓는다. 공통점은 요약과 항목을 따로 두지 않는다는 것이다.

### 지표 라벨

`app/dashboard/page.tsx:187-190`에서 라벨은 Open, Today, Overdue, Upcoming인데
설명은 한국어다. 한 화면에서 두 언어가 섞인다.

## 방향

### 색

바탕부터 파랑이 섞인다. 왼쪽 메뉴를 진한 남색으로 채워서 파랑이 포인트가 아니라
주 색이 되게 한다. 메뉴가 화면 왼쪽을 세로로 다 차지하므로 여기가 기조를 정한다.

| 토큰 | 값 | 쓰임 |
|---|---|---|
| `--paper` | `#DFE5EE` | 화면 바탕 |
| `--card` | `#F7F9FC` | 목록이 놓이는 면 |
| `--card-2` | `#FFFFFF` | 상세 패널 등 읽는 면 |
| `--navy` | `#16294A` | 왼쪽 메뉴 |
| `--navy-2` | `#1E3760` | 메뉴 안 선과 눌린 상태 |
| `--ink` | `#14202F` | 본문 |
| `--ink-2` | `#4A5A70` | 보조 |
| `--ink-3` | `#78879C` | 라벨과 날짜 |
| `--rule` | `#CFD8E5` | 가는 선 |
| `--rule-strong` | `#B3C0D2` | 구역을 나누는 선 |
| `--blue` | `#1B4FA8` | 링크, 지금 위치, 주 버튼 |
| `--blue-deep` | `#12376F` | 눌린 상태와 글자 위 파랑 |
| `--blue-wash` | `#DCE6F6` | 고른 행의 배경 |
| `--late` | `#A32017` | 기한 지남 |
| `--late-wash` | `#F7E3E0` | 그 배경 |
| `--soon` | `#8A5A00` | 오늘내일 마감 |
| `--soon-wash` | `#F7EDD8` | 그 배경 |

바탕을 순백으로 두지 않은 이유는 두 가지다. 흰 종이에 검정 글씨는 대비가 너무 세서
오래 보면 눈이 아프다. 그리고 바탕이 무채색이면 파랑이 아무리 있어도 포인트로만
읽힌다.

임박 색을 노랑이 아니라 어두운 갈색으로 내린 이유는 노랑 계열이 밝은 바탕에서 대비가
안 나오기 때문이다. 색만으로 구분하지 않고 항상 글자를 함께 쓴다.

### 글꼴

Geist를 걷어내고 IBM Plex로 간다.

- 본문과 UI는 IBM Plex Sans KR
- 숫자, 날짜, 라벨은 IBM Plex Mono

한글이 제대로 나오면서 스위스풍 성격이 있는 조합이다. 숫자 폭이 같아서 목록에서
세로줄이 맞는데, 날짜와 개수가 많은 화면이라 이게 실제로 크게 먹힌다.

### 구성

지표 카드 네 개를 없앤다. 숫자는 목록 위 필터 버튼 안으로 들어간다. 세는 일과
좁히는 일이 한 자리에서 끝난다.

본문은 두 단이다.

```
[남색 메뉴] [ 할 일 목록 ] [ 상세 또는 오늘 개요 ]
```

목록은 지금 `buildPriorityStream`이 만드는 것을 그대로 쓴다. 약속과 할 일을 종류가
아니라 급한 순으로 섞은 하나의 목록이다. 왼쪽에서 항목을 고르면 오른쪽이 그 항목의
상세로 바뀐다.

상세에 무엇이 들어가는지는 종류에 따라 다르다. 데이터가 다르기 때문이다.

| 종류 | 상세에 들어가는 것 |
|---|---|
| 약속 | 내용, 기한, 고객, 확정 여부, **근거 원문**, 출처(통화·문서·채팅) |
| 할 일 | 내용, 기한, 등록 시각. 근거 원문은 없다 |

근거 원문이 이 구성을 고른 이유다. 비서가 대화에서 할 일을 뽑아주는 게 OnQue의
핵심인데, 그게 맞는지 사용자가 확인할 방법이 지금 없다. 근거 문장을 옆에 붙이면
믿을지 말지가 그 자리에서 끝난다. 잘못 뽑힌 항목도 여기서 걸러진다.

다만 그게 되는 건 약속뿐이다. `Commitment` 테이블에는 `evidence`, `source_type`,
`source_id`, `room_id`가 있지만 `Todo`에는 `content`, `due_date`, `is_done`,
`created_at`이 전부다. 비서가 채팅에서 뽑아 만든 할 일인데도 어느 메시지에서
나왔는지 아무것도 남기지 않는다.

할 일에 근거를 남기려면 컬럼 추가와 마이그레이션, `_apply_extracted_actions` 수정이
필요하다. 백엔드 작업이라 이번 범위 밖으로 둔다. 별도 작업으로 뺀다.

아무것도 고르지 않았을 때 오른쪽은 비지 않는다. 오늘 개요가 들어간다.

- 다가오는 일정
- 최근 요약
- AI 사용량

별도 탭으로 빼지 않는 이유는 하루에 한 번 볼까 말까 한 자리가 되기 때문이다.
빈 패널로 두지 않는 이유는 화면 절반이 노는 것이기 때문이다.

### AI 사용량 표시

숫자만 보여주던 걸 20칸 눈금으로 바꾼다. 자동 정리 몫은 옅게 칠한다.

지금은 자동 정리가 누적 8건에서 멈추는데 사용자 호출도 같은 숫자를 올려서, 총
8에서 19 사이 구간에서는 자동 정리가 하루 종일 멈춰 있어도 화면이 20/20에서만
소진을 알린다. 눈금으로 그리면 그 상태가 그대로 보인다.

이 항목은 `docs/ai-call-budget-followups.md`의 UX 항목에 적혀 있던 것이다.

### 지표 라벨

Open, Today, Overdue, Upcoming을 한국어로 바꾼다. 필터 버튼 안으로 들어가면서
전체, 지남, 오늘, 이번 주, 확인 필요가 된다.

"내가 맡은 것"과 "비서가 넣은 것"은 넣지 않는다. `Todo`에도 `Commitment`에도
담당자 컬럼이 없고, 할 일이 사람이 만든 것인지 비서가 뽑은 것인지 구분할 값도
없다. 만들 수 없는 필터를 그리면 안 된다.

| 화면 | 할 일 |
|---|---|
| 대시보드 | 구성 전면 교체. 목록과 상세 두 단 |
| 채팅 | 색 전환. 말풍선과 비서 표시를 새 토큰으로 |
| 통화 요약, 문서 요약 | 색 전환. 업로드 영역과 진행 표시 |
| 이력 조회 | 색 전환. 목록 규칙을 대시보드와 맞춤 |
| 팀 공지, 그룹 관리 | 색 전환 |
| 로그인, 가입 | 색 전환. 남색 면을 써서 첫 인상에 기조를 실음 |
| 프로필 | 색 전환 |

## 순서

1. 토큰을 새 값으로 다시 정의한다. `globals.css` 한 곳
2. 공용 컴포넌트 다섯 개를 새 규칙으로 맞춘다. Button, Surface, StatusChip, Skeleton, BudgetNotice
3. 대시보드를 새 구성으로 다시 만든다
4. 하드코딩 색 111곳을 토큰으로 바꾼다
5. 나머지 화면을 훑으며 어긋난 곳을 잡는다

3번을 4번보다 먼저 두는 이유는, 대시보드에서 실제로 쓰이는 규칙이 확정돼야 나머지
화면을 어디로 맞출지 정해지기 때문이다.

## 범위 밖

- 기능 추가나 변경. API도 데이터도 그대로 둔다
- 다크 모드. 라이트만 만든다. 나중에 붙이려면 토큰이 이미 갈라져 있으니 값만 더하면 된다
- 모바일 전용 화면. 반응형은 지키되 별도 설계는 하지 않는다
- 컴포넌트 테스트 인프라 도입. 아래 한계 참고
- `Todo`에 근거 컬럼 추가. 백엔드 작업이라 별도로 뺀다

## 알려진 한계

할 일 상세에는 근거 원문이 없다. 데이터가 없어서다. 사용자 입장에서는 목록의 절반은
"왜 여기 있는지" 확인이 되고 절반은 안 되는 상태가 된다. 이 작업으로 완전히 풀리지
않는다는 것을 알고 넘어간다.

컴포넌트 테스트가 없다. jsdom과 testing-library가 없고 vitest가 `lib/**`만 돌린다.
그래서 이번 작업의 검증은 타입 검사, 빌드, 그리고 사람이 화면을 보는 것에 기댄다.
판정 로직을 담은 순수 함수는 테스트로 고정할 수 있지만, 컴포넌트가 그걸 실제로
부르는지는 확인할 수 없다. 이 저장소는 그 간극에서 이미 두 번 당했다(TS-035, TS-036).

eslint 에러 5건이 기준선으로 남아 있다. 이번 작업에서 늘리지 않는다.

## 검증

- 타입 검사 통과
- next build 성공
- vitest 기존 테스트 통과
- eslint 에러 5건 유지. 늘지 않음
- 하드코딩 색 검색 결과가 0에 수렴. `text-white`와 `bg-white`가 남아 있으면 실패
- 12개 화면을 320, 768, 1024, 1440에서 열어 가로 스크롤이 없는지 확인
- 본문과 바탕의 대비가 4.5 대 1을 넘는지 확인
- 키보드로 메뉴와 목록을 훑을 때 지금 어디인지 보이는지 확인
