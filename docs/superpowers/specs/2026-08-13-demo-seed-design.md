# 시연용 시드 스크립트 설계

**날짜:** 2026-08-13
**목표:** 사내 시연·포트폴리오 발표에서 OnQue가 끊김 없이 돌아가는 것을 보여줄 수 있게 한다.

## 배경

OnQue는 완성형 상용 서비스가 아니라, 이식할 패턴을 검증하는 프로젝트다. 이번 작업의
목적은 운영 준비가 아니라 **시연 준비**다. 들어가는 데이터는 전부 가짜이고, 실제
고객 정보는 넣지 않는다.

직전에 대시보드 프론트엔드 개편(R1)을 마쳤다. 본류 스트림과 요약 열이 전부 데이터에
의존하므로, 데이터가 없으면 방금 만든 화면이 빈 상태로만 보인다. 시연의 성패가
데이터 상태에 걸려 있다.

## 완료 기준

발표 직전 백엔드를 깨운 뒤, 아래가 끊김 없이 돌아가면 완료다.

1. 로그인 → 대시보드에 데이터가 차 있다 (빈 화면이 아니다)
2. 이미 요약된 통화·문서가 목록에 보인다 — Gemini 호출 0
3. 본류 스트림에서 급한 것을 확인하고 할 일을 완료 처리한다
4. 약속을 확인·무시하면 본류 스트림에 즉시 반영된다
5. 통화 녹음 1건을 올려 요약이 실제로 생성된다 — Gemini 호출 2

**시연 1회 총 호출 2건.** 무료 티어 하루 20건 안에서 여러 번 시연할 수 있다.

## 범위

### 만드는 것

`scripts/seed_demo.py` 하나. 그 외 신규 개발 없음.

### 명시적으로 범위 밖

가짜 데이터에는 지킬 것이 없어 뺀다. 실데이터로 전환하는 시점에 다시 꺼낸다.

- 개인정보 처리 근거·동의, 보관·삭제 정책, 감사 로그, PII 마스킹
- Gemini 업로드 파일 삭제 (`files.delete` 미호출 상태 유지)
- 유료 전환 (Gemini 종량, Render 유료) — 상용화 시점 과제
- 잔여 호출 한도 표시
- CI 구축, git 히스토리 정리, 에러 리포팅
- **초대 링크·이메일 발송** — 초대 기능은 이미 끝까지 동작한다(아래 참조)

### 초대 기능을 만들지 않는 이유

확인한 결과 초대는 이미 완결되어 있다.

| 단계 | 구현 위치 |
|---|---|
| 보내기 | `app/groups/page.tsx` → `inviteToGroupByEmail` |
| 받기·수락·거절 | `components/ReceivedInvitations.tsx` (대시보드·그룹·프로필 3곳에 렌더) |
| 백엔드 | `GET /me/invitations`, accept, decline (`routers/auth.py`) |
| 테스트 | `tests/test_group_invitations.py` 11개 — 백엔드 241개에 포함되어 통과 |

빠진 것은 "상대가 로그인하기 전에 알 방법"(이메일 발송)뿐이다. 시연에서는 초대를
장면으로 쓰지 않고, **발표 전 준비 단계에서 팀원 계정을 받는 수단**으로만 쓴다.
그러므로 시연 흐름에 초대가 등장하지 않고, 알림 부재가 문제되지 않는다.

## 설계

### 실행 형태

```bash
venv/bin/python scripts/seed_demo.py --group-id <ID>
```

`--group-id`는 필수다. 생략하면 실행을 거부한다. 대상을 명시하지 않은 채 지우는
스크립트가 도는 것을 막는다.

### 지우는 것과 지우지 않는 것

이 구분이 이 설계의 핵심이다. 시연 팀에는 초대로 들어온 실제 동료 계정이 있고,
시드를 다시 돌릴 때 그 사람들이 튕겨나가면 안 된다.

| 지운다 (시연마다 초기화) | 지우지 않는다 (한 번 들어오면 유지) |
|---|---|
| 약속 (`commitments`) | 사용자 계정 (`users`) |
| 할 일 (`todos`) | 그룹 멤버십 (`group_members`) |
| 일정 (`schedules`) | 그룹 자체 (`groups`) |
| 통화·문서 요약 (`documents`) | 초대 기록 (`group_invitations`) |
| 클라이언트 (`clients`) | 채팅방·메시지 |

즉 **콘텐츠만 갈아끼우고 사람은 건드리지 않는다.** 리허설을 몇 번 하더라도 팀 구성은
그대로고 화면 데이터만 처음 상태로 돌아간다.

지우는 범위는 항상 `group_id = <대상>` 조건으로 한정한다. 다른 그룹의 데이터는
어떤 경우에도 건드리지 않는다.

**삭제 순서는 참조 방향의 역순이다.** `commitments.client_id`가 `clients`를 참조하므로
`clients`를 먼저 지우면 FK 위반으로 죽는다. 약속 → 클라이언트 순으로 지운다. 나머지
(할 일·일정·요약)는 서로 참조하지 않아 순서에 자유롭다.

### 채우는 데이터

모든 날짜는 **실행 시점의 오늘(T)을 기준으로 상대 계산**한다. 절대 날짜를 박으면
다음 주에 시연할 때 "7일 지남"이 "14일 지남"으로 바뀌고 "마감 임박"이 이미 지난
것이 되어, 본류 스트림의 정렬 시연이 통째로 어긋난다.

**클라이언트** 3곳. 하단 ClientPanel과 약속의 `client_id` 연결에 쓴다.

**통화·문서 요약** 4건. `documents` 테이블에 직접 넣는다. `source_type`은 `call`과
`document`를 섞고, `summary`에는 미리 작성한 요약 텍스트를 넣는다.
`created_at`은 T-14 ~ T-2에 흩는다.

**약속** — 본류 스트림과 승인 게이트를 모두 보여줘야 한다.

| status | due_date | 의도 |
|---|---|---|
| `proposed` | T+1 | 승인 게이트 + "아직 확정 안 됨" 표시 |
| `proposed` | T+5 | 승인 게이트 (일괄 승인 시연용 복수 건) |
| `proposed` | 없음 | 기한 없는 약속 |
| `confirmed` | T-7 | 기한 지남 — 맥동 점 + "7일 지남" 칩 |
| `confirmed` | T-2 | 기한 지남 (정렬 확인: 7일 지남이 위) |
| `confirmed` | T+1 | 마감 임박 칩 |
| `confirmed` | T+10 | 기한 있음, 임박 아님 |
| `fulfilled` | T-3 | 스트림에 **안 나오는 것** 확인 |
| `dismissed` | T-5 | 스트림에 **안 나오는 것** 확인 |

`source_type`은 `call`·`document`·`chat`을 섞어 출처 라벨("약속 · 통화" 등)이
스트림에서 다양하게 보이게 한다.

**할 일**

| due_date | is_done | 의도 |
|---|---|---|
| T-7 | false | 기한 지남 (스트림 최상단 경쟁) |
| T-3 | false | 기한 지남 |
| T+1 | false | 마감 임박 |
| T+2 | false | 마감 임박 경계 (`DUE_SOON_DAYS = 2`) |
| T+10 | false | 기한 있음 |
| 없음 | false | 기한 없음 — 스트림 최하단 |
| T-1 | true | 완료된 것은 스트림에 **안 나오는 것** 확인 |
| 없음 | true | 완료된 것 |

**일정** 4건. `scheduled_date`를 T+1, T+3, T+6(7일 내 — 요약 열에 표시),
T+20(범위 밖 — 표시되지 않는 것 확인)로 둔다.

열린 항목(약속 7 + 할 일 6 = 13건)이 스트림 상한 8건을 넘으므로, 화면이 가득 찬
상태로 보이면서 우선순위 정렬이 실제로 일하는 것이 드러난다.

**담당자 배정은 없다.** `Todo`·`Commitment`·`Schedule` 모두 `group_id` 단위로만
스코프되며 개인별 배정 필드가 스키마에 없다. 팀에 멤버가 여럿이어도 데이터는 팀
공용이다.

### Gemini를 부르지 않는다

요약 결과는 미리 작성한 텍스트를 DB에 직접 넣는다. 시드가 실제 요약을 돌리면 한 번
실행에 하루 예산의 절반이 날아가 리허설을 할 수 없다. 요약 결과물은 텍스트일 뿐이고,
시연에서는 "이미 처리된 과거 건"으로 보이는 편이 오히려 자연스럽다.

살아 있는 요약 경로는 시연 중 라이브 1건으로 증명한다.

### 안전장치

1. `--group-id` 없으면 실행 거부
2. 대상 그룹이 없으면 명확한 메시지와 함께 종료
3. 실행 전 대상 DB 주소(비밀값 제외)와 **지울 항목의 테이블별 건수**를 출력하고
   확인을 받는다. 거부하면 아무것도 하지 않고 종료
4. 삭제와 삽입을 하나의 트랜잭션으로 감싼다. 중간에 실패하면 전부 되돌린다 —
   반쯤 지워진 상태로 남는 것이 가장 나쁘다
5. `--yes` 플래그로 확인을 건너뛸 수 있게 한다. 반복 리허설 때 쓴다

### 계정과 비밀번호

시드는 계정을 만들지 않는다. 발표자 계정은 이미 있고, 동료들은 초대로 들어온다.
따라서 스크립트에 비밀번호가 등장하지 않는다.

### 백엔드 깨우기

Render 무료 티어의 콜드스타트(실측 39초)는 유료 전환을 하지 않으므로 남는다.
발표 전에 요청을 한 번 쳐서 미리 소진시킨다.

```bash
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" <백엔드주소>/api/v1/groups
```

401이 돌아오면 정상이다(서버는 살아 있고 인증만 없는 상태). 이 한 줄을
`scripts/seed_demo.py` 상단 주석에 남긴다. 별도 점검 스크립트는 만들지 않는다 —
포트폴리오·시연 규모에 과하다.

기존 `.github/workflows/warm-backend.yml`(업무시간 워밍)은 그대로 둔다.

## 에러 처리

- 그룹 미지정·미존재 → 무엇이 잘못됐는지와 어떻게 고치는지를 함께 출력하고 종료
- DB 연결 실패 → 연결 대상을 알 수 있게 출력. 비밀값은 출력하지 않는다
- 삽입 중 실패 → 트랜잭션 롤백. 부분 적용 상태를 남기지 않는다
- 확인 프롬프트 거부 → 변경 없이 종료

조용히 실패하지 않는다. 모든 종료 경로가 무슨 일이 일어났는지 말한다.

## 테스트

이 스크립트는 데이터를 지운다. 검증 없이 쓰기에 위험하다. `tests/test_seed_demo.py`로
아래를 확인한다. 기존 pytest 구조(`tests/conftest.py`)를 따른다.

1. **멱등성** — 두 번 연속 실행하면 두 번째 실행 후 상태가 첫 번째와 같다
   (건수·상태 분포가 동일)
2. **멤버십 보존** — 그룹에 멤버가 있는 상태에서 실행해도 `group_members`와 `users`가
   그대로다. 이 설계에서 가장 중요한 안전 요건이다
3. **격리** — 다른 그룹의 약속·할 일·일정이 삭제되지 않는다
4. **상대 날짜** — 오늘을 주입해 실행했을 때 기한 지남·임박·기한 없음 항목이 의도한
   개수만큼 생긴다
5. **그룹 미지정 거부** — 인자 없이 실행하면 아무것도 지우지 않고 종료한다

기존 백엔드 테스트 241개는 그대로 통과해야 한다. 이 작업은 애플리케이션 코드를
건드리지 않는다.

## 미룬 것 — 상용화 시점에 다시 볼 것

실데이터를 넣기로 결정하면 아래가 다시 필요해진다. 지금 만들지 않을 뿐 사라진
문제가 아니다.

- **Gemini 업로드 파일이 Google에 남는다.** `client.files.upload()`는 있으나
  `files.delete()` 호출이 없다. 고객 통화가 우리 통제 밖에 체류한다
- **개인정보 처리 근거** — 외부 LLM 전송에 대한 위탁·제3자 제공 고지와 동의. 코드가
  아니라 문서와 절차의 문제이며 사람이 준비해야 한다
- **PII 마스킹** — 현재 본문을 로깅하지 않아 위험이 낮으나, 로거 차원의 강제 장치가
  없어 누군가 본문을 로깅하면 막을 것이 없다
- **무료 티어 한도** — 하루 20건(요약 1건당 2호출)은 팀 상시 사용을 못 버틴다
- **초대 알림** — 상대가 로그인할 이유를 모른다. 이메일 발송 또는 초대 링크가 필요
- **CI 부재** — 테스트 241개가 있으나 머지를 막는 장치가 없다
- **기동 시 환경변수 검증 부재** — `os.environ[...]` 직접 읽기로 `KeyError` 사망
  (TS-034 참조)
