## 데이터 무결성

**`_apply_extracted_actions`에 중복 제거가 없다.** 받은 대로 `db.add(Todo(...))` 한다.
채팅 병합이 추출 범위를 "새 메시지 1개"에서 "최근 20개"로 넓혔고, 프롬프트로 다시
좁혔지만 모델 순응도에 데이터 무결성을 걸고 있다. 어긋나면 상한 없이 매 턴 한 행씩
쌓인다. 위 "할 일 중복 생성" 실측에서 새는 게 확인되면 이걸 먼저 닫는다.

## 관측성

- **로그 포매터가 없어 `extra`가 출력에 안 나온다.** 선점 로그가 `consumer`·사용량을
  `message`에도 실어 우회하고 있으나, 근본 해결은 구조화 포매터 도입이다.
  `observability.md`가 요구하는 JSON 구조화 로그가 아직 아니다
- **`_granted`가 이번 선점의 결과 대신 `used_today(db)`를 다시 읽는다.** 동시 상황에서
  로그의 `used`가 실제 순번보다 클 수 있고 선점마다 SELECT가 한 번 더 나간다

## 테스트 인프라

- **컴포넌트 테스트가 없다.** jsdom·testing-library가 없고 vitest가 `lib/**`만 실행한다.
  판정 로직은 테스트로 고정됐으나 **컴포넌트가 실제로 그것을 부르는지는 검증되지 않는다.**
  이번 브랜치의 프론트 검증 전반에 걸리는 한계다
- **AST 검사가 보는 모듈이 하드코딩 3개다.** 새 라우터가 Gemini를 부르면서 목록에
  안 들어가면 검사 밖이다
- **AST 검사가 `claim=` 키워드의 존재만 본다.** `claim=lambda: True`를 넘겨도 통과한다.
  인자가 `call_budget.*_claimer()` 호출인지까지 보면 닫힌다
- **`claim()`의 롤백 격리를 이 하네스로 검증할 수 없다.** `StaticPool` + `:memory:`라
  모든 세션이 커넥션 하나를 공유한다. 운영 Postgres가 유일한 검증처다
  (동시 선점 초과 방지는 파일 SQLite로 커넥션을 갈라 검증했다)
